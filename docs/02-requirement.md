## 0. 前提（①から引き継ぐ原則）

- **入口非依存**: 顧客1人に「顧客レコード」1つ、来店ごとに「来店記録」が足される。紙・PDF・写真・音声メモ・録音・お客様のフォーム入力・既存ツールの持ち込みは、すべてこの2つへの入口。入口ごとに別の記録を作らない
- **マルチテナント SaaS**: サロン1店舗＝1テナント。サロン間でデータは決して混ざらない。スクールは配下サロンの記録をすべて見られる別ロール（閲覧のみ・閲覧履歴が残る）。テナントはスクールが作ってサロンに渡す（暫定。①未確定 4）
- **月1万円以内・小規模特化**: 基本料 + AI 従量の合計が中央値で月1万円以内（仮）。多店舗・POS・予約・在庫は作らない。画面数を増やさない
- **配布はストアの専用アプリが標準**: 同じ Web 画面をネイティブの殻で包み App Store / Google Play から配る。殻が録音のバックグラウンド継続・カメラ・通知を担う。PC・タブレットのブラウザからも同じ URL で使える
- **スマホ前提・入力させない**: 利用者は文字を打たず「確認して直す」だけで済む形を優先する。顧客を探すのは検索窓1つで、絞り込み条件は選ばせない
- **店の顧客は店の全員が見られる**: 権限の既定はサロン内の全顧客を全スタッフが閲覧・記録できる。担当限定はオプション。退職時の遮断で持ち出しを防ぐ
- **紙と併用**: 紙で続ける顧客・スタッフがいても成立する。紙を取り込む入口を常に残す
- **対象業種**: エステ・脱毛・眉毛・ネイル・まつエク等。美容室は対象外
- **AI は入口の変換器**: 音声・画像・PDF を「カルテ項目の候補」に変える役割に閉じ、保存は必ず人が確認してから行う。実費は従量で見える化する

## 2. 各機能の要件

### FUNC-01 サロン登録・初期設定

- **概要**: スクール（提供者）がテナントを作成してオーナーを招待する（暫定。①未確定 4）。オーナーは業種・入口／既存ツールの利用状況・スタッフを登録する。スクールが伴走して行う想定
- **事前条件**: スクールロールが存在する。オーナーが招待を受け取っている
- **正常フロー**: スクールがサロン名を入れてテナントを作成 → オーナーを招待 → オーナーが入り、業種（複数可）を選ぶ → 使っている入口／既存ツールをチェック式で申告（予約サイト・LINE フォーム・紙カルテ・紙の同意書・その他）→ スタッフを招待（任意）→ 完了後すぐホーム（FUNC-29）に進める
- **例外・バリデーション**: サロン名は必須。業種は対象業種から1つ以上。お客様の敬称はサロン設定で「様／さん／なし」から選び、既定は「様」（画面上は名前を大きく出す場所にだけ小さく添え、密な一覧では省く。お客様向け文面は常に通常サイズ）。1人のオーナーが複数サロンを持つことは初版では認めない（暫定）。申告した入口は後から変更でき、変更履歴を残す（FUNC-23 の集計が変わるため）。テナントは作成時点でスクール配下に紐づき、スクールが解除できる
- **受入基準**:
  - オーナーが招待を開いてからホームに到達するまで、必須入力は4項目以内
  - 申告した入口／既存ツールがサロン詳細に表示され、FUNC-23 の集計に反映される
  - 業種を選ぶと FUNC-05 の既定テンプレート（メニュー種別）が用意される
  - 作成したテナントが FUNC-23 の一覧に現れる

### FUNC-02 ログイン・ロール・権限

- **概要**: オーナー／スタッフ／スクールの3ロール。認証は **メールアドレス＋パスワード** を主とし、「この端末を記憶する」で30日間の再ログインを省く。忘れたときはメールの再設定リンク。（2026-10-08 変更。ワンタイムリンク方式は、毎回メールを開かせる方が現場の手間になるため不採用）**権限の既定はサロン内の全顧客を全スタッフが閲覧・記録できる**。小規模サロンはスタッフが互いの顧客を見る前提（①田中のゴール）
- **事前条件**: FUNC-01 で招待されている（オーナー・スタッフ）、またはスクールとして登録されている
- **正常フロー**: メールアドレスとパスワードを入力 → ログイン → 「この端末を記憶する」が有効なら以後30日は再入力不要。共有端末では来店記録ごとに施術者を選ぶ（FUNC-04）。パスワードを忘れたら再設定リンクをメールで受け取る
- **例外・バリデーション**: パスワードは8文字以上。連続5回失敗で10分ロック。再設定リンクは30分で失効。オーナーは設定・契約・削除・退職処理・データのダウンロードを行える。スタッフは顧客・来店記録の閲覧と記録ができ、設定と削除はできない。「担当限定」をオーナーが有効にした場合のみ、スタッフは担当顧客に限定される（Scope 2。暫定）。スクールは閲覧のみ（全サロンの全記録を見られる。編集不可）。停止されたアカウントは即時に一切の操作ができない。サロンをまたいだアクセスは認可以前に構造的に不可能にする（非機能要件・データ分離）
- **受入基準**:
  - 正しいメールアドレスとパスワードでログインでき、誤ったパスワードでは「メールアドレスかパスワードが違います」と出て入れない
  - 「この端末を記憶する」を有効にしてログインした端末は、30日以内なら再入力なしで開ける
  - 連続5回失敗すると10分間ログインできない
  - スタッフが同じサロンの任意の顧客を開いて来店記録を作れる
  - スタッフが設定画面・削除・退職処理を開けない
  - 停止直後のスタッフのセッションで操作すると拒否される
  - 別サロンの顧客 ID を指定しても存在しない扱いになる（存在の有無も漏れない）

### FUNC-03 顧客レコード管理

- **概要**: 顧客の登録・一覧・検索・詳細。入口を問わず1人1レコード。詳細画面は FUNC-06 の注意点と警告、来店記録の時系列、預かり書類、同意、契約をまとめて見せる
- **事前条件**: ログイン済み（FUNC-02）
- **正常フロー**: 顧客を追加（必須は呼び名1つ。暫定）→ 一覧・検索 → 詳細で来店記録・写真・書類・契約・注意点を時系列で見る
- **例外・バリデーション**:
  - **検索は検索窓1つ**。名前・ふりがな・電話番号の**部分一致**（先頭一致ではなく、どこかに含まれれば一致。「はる」で「はるか」「こはる」が出る）を、入力のたびに絞り込む。一致した部分は強調する。絞り込み条件（担当・来店日・業種など）は初版では持たない。来店記録の本文（自由メモ）の検索は Scope 2 以降
  - **呼び名と本名は別のデータ**（2026-10-08 確定）。呼び名は必須で1つの文字列（店の流儀のまま）。本名は **姓・名・せい・めい** の4項目に分け、すべて任意。電話番号・LINE 表示名・生年月日も任意。後から足せる
  - 本名の用途: 契約書・同意書・特商法の書面の宛名、お客様へのメッセージの宛名（「姓 様」。姓が無ければ呼び名）、CSV 持ち込み（FUNC-11）の姓名列との対応、書類抽出（FUNC-28）の氏名、名寄せ（FUNC-12）の照合
  - 名を入れたとき、呼び名が空なら名を呼び名の候補にする。呼び名だけで登録した顧客は、フォーム（FUNC-10）・書類抽出（FUNC-28）・持ち込み（FUNC-11）から本名が入った時点で埋まる
  - 敬称はデータに含めず、表示時にサロン設定（FUNC-01）の敬称を付ける
  - **初回来店日**を独立した項目として持つ。来店記録とは別で、持ち込み（FUNC-08・11）時にも設定できる。新規／再来の判定（FUNC-04）はこの日付で行う
  - **禁忌・安全上の注意**を構造化して持つ（妊娠・服薬・日焼け・既往歴・金属アレルギー・光過敏など。メニュー種別ごとの既定リスト + 自由記述）。FUNC-06 の警告と FUNC-04 の当日チェックの元になる
  - 電話番号が既存顧客と一致したら登録時に重複候補を知らせる（FUNC-12 の簡易版）。削除は FUNC-16 の手順のみ
  - 顧客は外部 ID（種類と値の組。例: LINE ユーザー ID、予約サイトの顧客番号）を複数持てる。初版では画面に出さなくてよいが、構造として最初から持つ。外部 ID は FUNC-11・12・27 が名寄せの鍵として使う
- **受入基準**:
  - 呼び名だけで顧客を登録でき、所要タップ数は3以内
  - 姓・名を入れた顧客は、送付文面の宛名が「姓 様」になり、未入力の顧客は呼び名になる
  - 名だけ入れて呼び名を空にすると、呼び名の候補に名が入る
  - 検索窓に名前または電話番号の一部を2文字入れると、入力のたびに一覧が絞り込まれる。絞り込み条件の選択 UI は存在しない
  - 一覧は最近来店した順を既定とする
  - 詳細では、来店記録・写真・書類・フォーム回答の由来の違いに関わらず、同じ時系列に並ぶ
  - 禁忌を1つ登録すると、顧客詳細の最上部に警告として出る（FUNC-06）
  - 1人の顧客に種類の違う外部 ID を2つ以上持たせられ、同じ種類・同じ値の外部 ID は同一サロン内で1人にしか付かない

### FUNC-04 来店記録（カルテ）管理

- **概要**: 来店1回につき1件の記録。施術内容・項目（FUNC-05 のテンプレート）・自由メモ・写真・施術者・次回への申し送りを持つ。手入力、写真のみ、紙取り込み、音声メモ、録音のどれから作っても同じ記録になる。**分析と再来店推奨のために、来店記録は「予約・来店・会計」の最小データも兼ねる**: 来店種別（体験／通常）、施術メニュー、金額（施術／物販／コース消化の区別つき。任意）、次回予約日（任意）、新規か再来か（自動判定）、来店経路（予約サイト／LINE／紹介／飛び込み／不明）。**当日の禁忌チェック**（FUNC-03 の禁忌リストから、メニュー種別に応じた確認項目）を持つ。予約管理・会計システム自体は作らない
- **事前条件**: 顧客が存在する
- **正常フロー**: 下部タブ「＋記録」で「誰の記録ですか？」のシートを開き、賢い既定（今日の未記録が1人ならその人）・今日来る人・検索・最近来た方・新規登録のいずれかで相手を決める（記録かお客様追加かを先に選ばせない。新規は検索に一致が無いときに呼び名だけで作ってそのまま進む）→ または顧客詳細から「来店を記録」→ 施術者を選ぶ（既定は操作者）→ 日付は今日が既定 → 当日の禁忌チェック → 項目を埋める（入口により候補が入っている）→ 確認して保存。その場で終わらなければ「記録がまだ」として残し、閉店後にホームから続きができる
- **例外・バリデーション**:
  - 来店日は必須（既定で今日。日本時間で判定）。項目は空でも保存できる（記録ゼロより空の記録を優先する）
  - 施術者は共有端末を想定して記録ごとに選べる。既定は操作者
  - 禁忌確認が必要なメニュー種別では、当日チェックが未記入のまま保存しようとすると確認を挟む（保存は止めない。チェック漏れが KPI に出る）
  - 保存後の編集は履歴を残す（誰が・いつ・何を）。同一顧客・同一日に2件目を作るときは確認を挟む。**来店記録の削除**は、スタッフは自分が作った記録を当日中のみ、それ以外はオーナーのみ。削除しても履歴に「削除した」事実と削除前の内容が残る
  - 金額・次回予約日・来店経路・来店種別はすべて任意で、空でも保存できる。来店種別の既定は「通常」。顧客の初回来店で「体験」を選ぶと KPI「成約率」の分母になる
  - 新規か再来かは、顧客の初回来店日（FUNC-03）とこの来店日が同じなら「新規」、それ以外は「再来」と自動判定し、手で直せる。持ち込んだ既存顧客（FUNC-11）は初回来店日が過去なので「新規」にならない
  - 次回予約日は来店日より後の日付のみ。メニューは初版では自由入力（候補は過去の入力から出す）とし、メニューマスタは FUNC-26
- **受入基準**:
  - 「＋記録」から、今日の未記録が1人のときは1タップでその人の来店記録に入れる
  - 「＋記録」の検索で一致が無いとき、入力した文字列を呼び名にして登録と来店記録を1本の流れで進められる
  - 項目が1つも埋まっていなくても「来店した」事実だけで保存できる
  - 入口の違う4種類（手入力・紙取り込み・音声メモ・写真のみ）で作った記録が、顧客詳細で同じ形で表示される
  - 記録を編集すると、編集前の内容が履歴として参照できる
  - 施術者を操作者以外に変えて保存でき、顧客詳細にその施術者名が出る
  - 禁忌確認が必要なメニューで当日チェック未記入のまま保存すると、確認が出る
  - 金額・次回予約日・来店経路が空でも保存できる
  - 初回来店日と同日の来店記録は「新規」、持ち込み顧客の最初の記録は「再来」と付く
  - 保存を途中でやめた記録が、ホームの「記録がまだ」に出て続きができる
  - 次回予約日を入れた顧客は、その日まで FUNC-19 の声かけ一覧に出ない

### FUNC-05 カルテ項目テンプレート

- **概要**: **メニュー種別**（フェイシャル・痩身・脱毛・眉毛・ネイル・まつエク等）ごとの既定項目セットと、サロンが足せる独自項目。1サロンが複数のメニュー種別を持てる（脱毛＋フェイシャルなど）。項目には型（短文・長文・選択・数値・写真・チェック）がある。**各項目は「問診フォームに出す」のオンオフと、お客様向けの表示名（任意。例: スタッフ向け「肌の状態」→ お客様向け「気になっていること」）を持つ**（2026-10-08 追加。FUNC-10 の項目はここで決まる）。各メニュー種別は禁忌確認の既定リストを持つ。**友人のスプレッドシート受領後に既定項目を見直す（暫定）**
- **事前条件**: FUNC-01 で業種が決まっている
- **正常フロー**: 業種を選ぶと該当するメニュー種別の既定項目が入る → サロンは項目を追加・非表示・並べ替えできる → 来店記録（FUNC-04）はメニューに応じたテンプレートで作られる
- **例外・バリデーション**: 既定項目は削除ではなく非表示にする（過去記録の表示を壊さない）。項目を変えても過去の来店記録の値は消えない。項目名の重複は不可。AI 抽出（FUNC-08・13・14・28）はテンプレートの項目名と型を手がかりにする
- **受入基準**:
  - 業種を2つ選ぶと、両方のメニュー種別の既定項目が使える
  - 項目を非表示にしても、過去の来店記録ではその値が読める
  - 独自項目を追加すると、次の来店記録から入力欄に現れ、AI 抽出の候補対象にも入る
  - 項目の「問診フォームに出す」をオンにすると、お客様向けフォーム（FUNC-10）にお客様向け表示名で現れ、オフにすると消える
  - メニュー種別ごとに禁忌確認の既定リストが異なる

### FUNC-06 注意点と安全上の警告の表示

- **概要**: 顧客詳細の最上部に2種類を出す。**安全上の警告**（FUNC-03 の禁忌から機械的に生成。常に表示）と、**今回気をつけること**（人が確定した注意点。初版は手動入力。FUNC-18 ができたら自動生成の候補が入り、人が確定する）
- **事前条件**: 顧客が存在する
- **正常フロー**: 顧客詳細を開く → 最上部に警告（禁忌があれば）と注意点（無ければ「まだありません」と入力導線）→ 来店記録保存時に「次回への申し送り」を書くと、注意点に反映される
- **例外・バリデーション**: 警告は人が消せない（禁忌そのものを FUNC-03 で直す）。注意点は常に人が確定した内容のみ表示する。自動生成の候補は「候補」と明示し、確定するまで表示欄には出ない
- **受入基準**:
  - 顧客詳細を開いたとき、スクロールせずに警告と注意点が読める
  - 禁忌を登録した顧客では、警告が注意点より上に出る
  - 来店記録の「次回への申し送り」を保存すると、次に顧客詳細を開いたときの注意点に反映されている
  - 候補と確定済みが見分けられる

### FUNC-07 写真の撮影・添付

- **概要**: スマホのカメラで撮った写真を、その来店記録に結びつける。施術前・施術後のラベルを付けられる。撮影には記録用の写真同意（FUNC-15）が前提
- **事前条件**: 来店記録が作成中または存在する
- **正常フロー**: 来店記録から「写真」→ 撮影またはカメラロールから選択 → 前／後のラベル → 保存。顧客詳細では来店ごとに並び、拡大できる
- **例外・バリデーション**: 1来店あたりの枚数上限は 20 枚（暫定）。端末側で長辺 2,000px 程度に縮小してから送る。電波が無いときは端末に保持し、つながったら送る。写真はそのサロンの利用者のみが見られる。写真の URL は短期有効で、推測できない。写真同意が未記録の顧客では撮影前に同意の確認を挟む
- **受入基準**:
  - 撮影から保存まで3タップ以内
  - 顧客詳細で、来店をまたいで施術後写真だけを時系列で並べて見られる（経過比較）
  - 別サロンの利用者は写真 URL を知っていても閲覧できない
  - 電波を切った状態で撮影しても、復帰後に保存される

### FUNC-08 紙カルテの撮影取り込み

- **概要**: 紙カルテを撮影すると、テンプレート（FUNC-05）の項目に沿って内容の候補を抽出し、確認して保存する。元の画像は来店記録に残る
- **事前条件**: 顧客が存在する、または取り込み時に新規作成する。AI 利用上限（FUNC-25）に達していない
- **正常フロー**: 顧客詳細から「紙カルテを取り込む」→ 撮影（複数枚可）→ 抽出結果が項目ごとに並ぶ → 間違いだけ直す → 1枚の紙に複数回の来店が書かれていれば来店ごとに分けて保存 → 元画像も保存。最も古い来店日を初回来店日（FUNC-03）の候補にする
- **例外・バリデーション**: 読めない箇所は空欄のまま「読めませんでした」と示し、捏造しない。元画像は必ず残し、抽出結果と並べて確認できる。日付が読めないときは手で入れる。上限到達時は撮影と元画像保存だけ行い、抽出は後回しにできる。処理は非同期で、結果はホーム（FUNC-29）の「確認待ち」に出る
- **受入基準**:
  - 撮影開始から保存まで、手直し込みで1分以内に収まる操作数（手直し箇所3以下の場合）
  - 読めない箇所に推測の値が入らない（空欄と明示）
  - 保存後、来店記録から元画像を開ける
  - 複数来店が書かれた紙から、来店日ごとに分かれた記録ができる
  - 受入用の実際の紙カルテ（友人提供。要手配）で、記載項目の 8 割以上が正しく項目に入る（暫定。分母は紙に記載のある項目数）

### FUNC-09 書類（PDF）の預かり

- **概要**: 契約書・概要書面・同意書・問診票などの PDF（または写真）を顧客に紐づけて預かる。原本はいつでも開ける。項目の抽出は FUNC-28（Scope 2）で、預かりだけで価値が成立する
- **事前条件**: 顧客が存在する
- **正常フロー**: 顧客詳細から「書類を預ける」→ ファイル選択または撮影 → 書類の種類（契約書／概要書面／同意書／問診票／その他）と日付を確認 → 保存。同意書なら FUNC-15 の同意記録を、契約書なら FUNC-22 の契約を手で紐づけられる
- **例外・バリデーション**: 原本は改変せず保存する。ファイル名に日本語が含まれても預かれる（保存名は内部で変換し、元の名前は別に保持する）。1件 20MB まで（暫定）。書類はそのサロンの利用者のみが見られ、URL は短期有効
- **受入基準**:
  - 預けた PDF を顧客詳細から開け、元のファイル名で表示される
  - 書類の種類で絞って一覧できる
  - 別サロンの利用者は URL を知っていても開けない

### FUNC-10 お客様セルフ入力フォーム（事前問診）

- **概要**: **お客様が自分のスマホで開く公開 Web ページ**（サロンのアプリの外。ログイン不要。お客様にアプリは入れさせない）。サロンごとの公開リンクを LINE 公式アカウントのリッチメニューや店頭の QR コードから開き、問診項目に自分で入力する。回答はその人の顧客レコード（新規または既存）になる。LINE 連携そのもの（FUNC-27）が無くても動く。来店時にリンクを持っていないお客様には、サロンのタブレットでこのページを開いて渡してもよい（同意画面と同じ使い方）
- **事前条件**: フォームの構成は **テナント（サロン）が自由に変えられる**。固定部分は「お名前・ふりがな・電話番号」と「同意（要配慮情報・写真）」のみ。それ以外は FUNC-05 の項目のうち「問診フォームに出す」をオンにしたものが、お客様向け表示名と設定した順番で並ぶ。「体調について」の選択肢はそのメニュー種別の禁忌リストから出る。サロンは設定から「フォームを確認する」で実際の画面を見られ、リンクのコピーと QR コードの保存ができる
- **正常フロー**: お客様がリンクを開く → 氏名・連絡先・問診項目・禁忌の自己申告を入力 → 要配慮情報の取得同意と写真同意にチェック（FUNC-15）→ 送信 → サロンのホームに「未処理の回答」として届く → サロンが既存顧客と結びつけるか新規作成するかを確認
- **例外・バリデーション**: 公開リンクは推測できない文字列。回答は送信時点で顧客レコードに直接書き込まず、サロンが確認して取り込む（なりすまし・いたずら対策）。未処理の回答も要配慮情報を含むため同じ保護下に置く。同意チェックが無いと送信できない。お客様はログインしない
- **受入基準**:
  - お客様がログインせずに回答を送信できる
  - 回答がホームの「未処理の回答」に出て、既存顧客への結びつけと新規作成の両方ができる
  - 禁忌の自己申告が、取り込み後に FUNC-03 の禁忌として入り、FUNC-06 の警告に出る
  - 同意チェック無しでは送信できない

### FUNC-11 既存顧客一覧の持ち込み

- **概要**: 予約サイト等から出力した顧客一覧（CSV）を取り込んで顧客レコードにする。1回きりの移行用。持ち込んだ顧客は既存顧客として扱う
- **事前条件**: サロンがファイルを用意している。スクールが伴走する想定
- **正常フロー**: ファイルを選ぶ → 列と顧客項目の対応を確認（姓・名（または「氏名」1列をスペースで姓名に分割）・せい・めい・呼び名（無ければ名を既定）・電話・初回来店日・外部 ID・メモなど）→ 取り込み結果（件数・重複候補）を確認 → 確定
- **例外・バリデーション**: 文字コードは UTF-8 と Shift_JIS の両方を受ける。列対応はサンプル行を見せて確認させる。初回来店日の列が無ければ「取り込み日より前（不明）」として扱い、新規判定の対象外にする。電話番号一致は重複候補として FUNC-12 に送る。取り込みは全件成功か全件取り消しのどちらか。やり直せるよう取り込み単位を記録する
- **受入基準**:
  - 予約サイトから出した実ファイル（友人提供。要手配）が、列対応の確認だけで取り込める
  - 持ち込んだ顧客の最初の来店記録が「新規」にならない
  - 途中で失敗した取り込みは1件も残らない
  - 取り込み単位でまとめて取り消せる

### FUNC-12 名寄せ（重複のまとめ）

- **概要**: 電話番号・氏名・ふりがな・LINE 表示名・外部 ID の一致から同一人物の候補を出し、確認して1人にまとめる。**「片方を残す」ではなく「2人分を合わせて1人にする」**。来店記録・写真・書類・同意・契約・外部 ID はすべて残り、顧客の属性は項目ごとにどちらの値を使うか選ぶ
- **事前条件**: 顧客が2件以上ある
- **正常フロー**: 候補ペアを見る → 根拠を確認 → 属性ごとに値を選ぶ（既定は自動で埋まる）→ まとめる → 1人の時系列に全記録が並ぶ
- **例外・バリデーション**（2026-10-08 改訂）:
  - **記録は消さない**。来店記録・写真・音声・書類・同意・契約・フォーム回答・外部 ID は両方の分をすべて統合する。同じ日の来店記録が両方にある場合も2件のまま残し、「重複の可能性」バッジを付ける（人が後で片方を削除できる）
  - **属性は項目ごとに選ぶ**。呼び名・ふりがな・本名・電話番号・LINE 表示名・生年月日・初回来店日・メモ・注意点について、両方の値を並べて表示する。既定は「空でない方」、両方あって違う場合は「更新が新しい方」を仮選択し、人が変更できる
  - **和集合にするもの**: 禁忌・外部 ID・同意（種類ごとに取得日の古い方を取得日、撤回があれば撤回を優先）
  - **初回来店日は古い方**。来店回数は合算
  - 自動ではまとめない（必ず人が確認する）。候補の根拠（何が一致したか）を示す。まとめは取り消せる（暫定 30 日。取り消すと属性の選択前の2人に戻る）
- **受入基準**:
  - 電話番号が同じ2件が候補として出る
  - 片方にだけ生年月日があるとき、まとめ後の顧客に生年月日が入っている（空でない方が選ばれる）
  - 両方に電話番号があり値が違うとき、まとめ前にどちらを使うか選ぶ画面が出て、選ぶまでまとめられない
  - まとめた後、両方の来店記録が1人の時系列に並び、件数が合算されている
  - 片方の禁忌がもう片方に無いとき、まとめ後は両方の禁忌が警告に出る
  - まとめを取り消すと元の2件に戻る

### FUNC-13 音声メモ → カルテ自動入力

- **概要**: 施術後にスタッフがスマホに向かって話した短い音声を文字にし、テンプレート項目の候補に振り分ける。お客様の声は入らない。その場でも、閉店後にホームの「記録がまだ」からでもできる
- **事前条件**: 来店記録が作成中。AI 利用上限に達していない
- **正常フロー**: 来店記録から「話して記録」→ 録音開始 → 話す（30 秒〜数分）→ 停止 → 文字起こしと項目候補が出る（非同期。結果はホームの確認待ちにも出る）→ 確認して保存。文字起こし全文も自由メモに残せる
- **例外・バリデーション**: 候補は項目ごとに「候補」と分かる表示で、確定するまで保存されない。聞き取れない部分は空欄にし捏造しない。音声ファイルは文字起こし完了後 30 日で削除する（暫定）。1件あたりの長さ上限は 10 分（暫定）。電波が無いときは端末に保持し、つながったら送る。上限到達時は録音だけ保存し、後で処理できる。送る前に無音区間を削って文字起こし量を減らす
- **受入基準**:
  - 録音開始・停止・保存の3操作で来店記録が作られる
  - 話した内容のうちテンプレート項目に当たるものが、該当項目の候補に入る（受入用の台本3本で確認）
  - 閉店後に「記録がまだ」の来店を開いて音声メモから記録を完成できる

### FUNC-14 会話録音 → カルテ自動入力

- **概要**: 施術中の会話を録音し、FUNC-13 と同じ流れでカルテ項目の候補にする。出口は FUNC-13 と共通。**録音の同意記録は持たない**（2026-10-08 確定。会話の当事者による録音は本人同意を法的要件としないため。記録する内容の同意は FUNC-15 の要配慮情報の同意で担保する。店内掲示などの案内は運用で行う）
- **実現方式（2026-10-08 確定: アプリ版が標準）**:

- **事前条件**: AI 利用上限に達していない
- **正常フロー**: Web 版は、来店記録から「会話録音」→ 録り方の案内 → 録音ファイルを取り込む（共有メニューまたはファイル選択）→ 無音・BGM 区間を削って文字起こし → 候補を確認して保存。アプリ版は、同じ画面の「録音」で開始 → 施術 → 停止 → 以後同じ

- **受入基準**:
  - 60 分の録音を取り込むと、無音を除いた分だけが文字起こしに使われ、FUNC-25 の利用量に加算される
  - FUNC-13 と同じ確認画面に至る（出口が共通）
  - アプリ版で録音中に画面を消灯し他のアプリを 5 分使っても、録音が途切れない
  - Web 版では録音アプリのファイルを取り込んで同じ確認画面に至る

### FUNC-19 再来店タイミングの推奨

### FUNC-21 全体分析

- **概要**: サロン全体の周期内再来率・体験からの成約率・客単価・次回予約率・来店経路別の再来率・メニュー別の再来率と売上・失客候補・禁忌確認率などを集計し、改善点の候補を文章で示す。材料は来店記録（FUNC-04）の最小データと契約（FUNC-22）。予約サイトの予約データ（キャンセル率等）が必要なら、CSV の取り込みを任意で足す。後に FUNC-24 でスクールも見る
- **事前条件**: 来店記録が一定数（暫定 100 件）以上

- **例外・バリデーション**: 件数不足のときは「まだ分析に足りない」と件数を示す。改善点候補は集計の数字を根拠として併記する。顧客個人を特定する表現を含めない。再来率は 90 日固定ではなくメニュー周期の 1.5 倍以内で測る（①KPI）

  - 金額が入っていない来店が多い場合、客単価に「母数が少ない」と注記が出る

### FUNC-25 AI 利用量の見える化と上限

- **概要**: サロンごとに AI 利用量（文字起こしの分数・画像／PDF の抽出回数・生成回数）を機能別に数え、**月の請求見込み金額を常に表示**する。上限到達で AI 機能を保留に切り替える。従量課金の根拠データになる
- **事前条件**: サロンに上限値が設定されている（既定値あり。暫定。決定権はスクール。①未確定 4）

  - 上限を上げると保留分が処理される
  - 機能別（音声メモ／会話録音／紙取り込み／書類抽出／生成）の内訳が見える

### FUNC-26 メニューマスタと標準価格・周期

- **概要**: サロンのメニュー（名前・メニュー種別・標準価格・区分: 施術／物販／コース・**推奨来店周期**）を登録する。来店記録でメニューを選ぶと金額が既定で入り、周期が FUNC-19 の推奨に使われる。会計システムではなく、入力の手間を減らすための辞書
- **事前条件**: FUNC-01 でサロンがある
- **正常フロー**: 設定からメニューを登録 → 来店記録でメニューを選ぶ → 標準価格が金額欄に入る → 必要なら金額を直して保存
- **例外・バリデーション**: 標準価格・周期は任意。周期が無いメニューはメニュー種別の既定周期を使う。メニューを削除しても過去の来店記録のメニュー名と金額は残る。来店記録に入った金額は来店時点の値として保持し、後からマスタの価格を変えても過去は変わらない

### FUNC-27 LINE 連携（Messaging API / LIFF）

- **概要**: サロンが持つ LINE 公式アカウントを本ツールに接続する。友だち追加時に LINE ユーザー ID を外部 ID（FUNC-03）として受け取り、問診フォーム（FUNC-10）を LINE 内（LIFF）で開くことで回答をその LINE ユーザーに自動で紐づける。施術内容の送付（FUNC-20）と声かけ（FUNC-19）を LINE のメッセージとして送る
- **事前条件**: サロンが LINE 公式アカウントを持ち、Messaging API の設定（チャネル作成・Webhook 登録）を終えている。スクールが伴走する想定。送付・声かけは FUNC-15 の送付同意が前提
- **正常フロー**: 設定で LINE を接続 → お客様が友だち追加 → LINE ユーザー ID が「未紐づけ」として届く → お客様が LINE 内でフォームを開いて回答 → 回答と LINE ユーザー ID が同じ顧客レコードに入る（既存顧客なら電話番号等で候補を出し確認して結びつける）→ 来店後、顧客を選んで「LINE で送る」
- **例外・バリデーション**: LINE の API 設定が無いサロンでも FUNC-10・19・20 はリンクとコピーの形で動く（LINE 連携は上乗せ）。送信通数は LINE 側のプラン上限があるため、月の送信数をサロンごとに表示し、上限に近づいたら知らせる。お客様からの返信は本ツールで受けず、サロンの LINE アプリで対応する。LINE の資格情報（チャネルシークレット・トークン）はサーバー側にのみ保存し、ログや画面に出さない
- **受入基準**:
  - 友だち追加したお客様が LINE 内のフォームに回答すると、サロン側で確認するだけで LINE ユーザー ID 付きの顧客レコードができる
  - 同じお客様が再度フォームを開いたとき、新しい顧客が増えず既存の顧客に回答が追加される
  - 送付同意の無い顧客には「LINE で送る」が使えない
  - LINE 未接続のサロンでも、FUNC-10・19・20 がリンクとコピーの形で動く

### FUNC-28 書類からの項目抽出

- **概要**: 預かった書類（FUNC-09）から重要項目（氏名（姓・名に分けて）・連絡先・生年月日・同意の種類と日付・アレルギー・既往歴・禁忌・契約内容: コース名・回数・金額・契約日・有効期限）を抽出し、確認して顧客情報（FUNC-03）・同意（FUNC-15）・契約（FUNC-22）に反映する
- **事前条件**: 書類が預かられている。AI 利用上限に達していない
- **正常フロー**: 預かった書類の「項目を読み取る」→ 書類種別に応じた抽出結果が並ぶ → 既存の値と違う項目は両方を見せて選ぶ → 反映。処理は非同期で、結果はホームの確認待ちに出る
- **例外・バリデーション**: 既存の値を黙って上書きしない。読めない項目は空欄と明示し捏造しない。同意書なら同意記録の候補、契約書なら契約の候補、問診票なら禁忌の候補を出し、1タップで確定できる
- **受入基準**:
  - 抽出された氏名が既存と違うとき、黙って上書きされない
  - 同意書を読み取ると、同意記録の候補が出て1タップで確定できる
  - 契約書を読み取ると、契約の候補（回数・金額・契約日）が出て確定できる
  - 問診票の禁忌欄が FUNC-03 の禁忌候補になる

### FUNC-29 今日のホーム

- **概要**: ログイン後の最初の画面。「次のお客様」ヒーロー（施術前「来店を確認する」／施術中「記録を残す」／全員記録済みの完了、の3状態のどれか1枚）と「今日の流れ」（時刻順。各行に新規／n回目・メニュー・前回日・記録状態）、「今日の記録の進み」、「あとで」（記録がまだ・確認待ち・未処理の回答）を1画面に出す。検索窓もここに置く
- **今日の流れのデータ源（2026-10-08 明記）**: 本ツールは予約管理をしないため、**予約サイト・Instagram DM・電話で受けた予約は自動では入らない**。今日の流れに並ぶのは次の3つだけで、画面にもその旨を正直に書く
  1. 来店記録の「次回予約日」が今日の顧客（前回の退店時に次回を入れた分）
  2. 今日作った来店記録（記録済み・記録中）
  3. **その日に手で足した「今日来る人」**（朝に顧客を選ぶだけ。時刻は任意。30秒で済ませる想定）
  - 予約サイトや DM の予約は、朝の「今日来る人を足す」か、来店時にそのまま「記録を始める」で入る。入れなくても記録には支障がない（今日の流れは補助で、記録の必須条件ではない）
  - データ源の説明は画面に出さない（利用者には不要）。初回の空状態でだけ「予約はこれまでどおり予約サイトや LINE で」と添える
  - 各行には利用者が判断に使う情報を出す: **新規か再来か（n回目）**、メニュー、前回来店日、久しぶりなら間隔、体験、警告、記録の状態
  - 外部の予定を自動で取り込む手段は FUNC-31（Scope 3）
- （旧記述）「今日の来店」（次回予約日が今日の顧客 + 今日作った来店記録）、「記録がまだ」（保存が完了していない来店記録・直近の来店で項目が空のもの）、「確認待ち」（AI 処理が終わって確認を待つ候補）、「未処理の回答」（FUNC-10）を1画面に出す。ここから顧客詳細・来店記録・確認画面に直接入る。検索窓もここに置く
- **事前条件**: ログイン済み
- **正常フロー**: アプリを開く → ホーム → 今日の来店の顧客をタップして来店記録へ、または「記録がまだ」から続きへ、または確認待ちを開いて確定
- **例外・バリデーション**: 日付の境界は日本時間。「記録がまだ」は来店日から 7 日で自動的に一覧から消え（記録自体は残る）、件数バッジだけ残す。スクールロールにはこの画面の代わりに FUNC-23 を出す
- **受入基準**:
  - 次回予約日が今日の顧客が「今日の流れ」に出る
  - 朝に「今日来る人」として顧客を選ぶと、時刻なしでも今日の流れに出る
  - 今日の流れが空でも「記録を始める」から来店記録を作れる（予定が無いことは記録の障害にならない）
  - 保存を途中でやめた来店記録が「記録がまだ」に出て、タップで続きができる
  - 音声メモの処理が終わると「確認待ち」に出て、確定すると消える
  - 検索窓に入力すると FUNC-03 の検索結果に切り替わる

### FUNC-31 外部の予定の取り込み

- **概要**: 「今日の流れ」に外部の予定を候補として出す。経路は2つ。(a) サロンが Google カレンダーに予約を入れている場合、読み取り専用で当日の予定を取り込む。(b) 予約サイト（サロンボード等）の予約通知メールを本ツールの専用アドレスに転送してもらい、顧客名・日時・メニューを読み取る。どちらも「候補」として出し、顧客への結びつけは人が確認する
- **事前条件**: (a) Google アカウントの読み取り許可。(b) 転送設定（スクールが伴走）
- **正常フロー**: 設定で接続 → 朝、今日の流れに「外部の予定（候補）」が並ぶ → 顧客に結びつける（名前一致は自動候補）→ 以後は通常の流れ
- **例外・バリデーション**: 予約サイトに公開 API は無いため、メール転送以外の手段は採らない。メールの書式変更で読み取れない場合は「読み取れませんでした」と原文を表示し、手で足せる。カレンダーの予定名から顧客を特定できない場合は未紐づけのまま出す。本ツールから外部に書き戻さない（予約の変更は予約サイト側で行う）
- **受入基準**:
  - Google カレンダーに今日の予定がある状態で接続すると、今日の流れに候補として出る
  - 予約通知メールを転送すると、顧客名・時刻・メニューが候補として出て、既存顧客に1タップで結びつけられる
  - 読み取れなかったメールは原文を見て手で足せる

### FUNC-30 データのダウンロードとエクスポート

- **概要**: 2段階。**(a) CSV ダウンロード（Scope 1）**: 顧客データ（1人1行。呼び名・姓名・ふりがな・電話・LINE 表示名・生年月日・初回来店日・来店回数・最終来店日・禁忌・外部 ID）と来店データ（1来店1行。来店日・顧客・施術者・メニュー・金額・来店種別・来店経路・次回予約日・項目の値・申し送り）を期間指定で CSV に出す。Excel・スプレッドシートで開ける（UTF-8 BOM 付き）。**(b) 全データの一式（Scope 2）**: 写真・書類の原本・音声・同意のサイン画像・編集履歴まで含めた一式を期限付きリンクで持ち出す。解約やスクール離脱の際に囲い込みをしない
- **事前条件**: オーナー権限
- **正常フロー**: 設定 → データ → 「顧客データ」「来店データ」を期間を選んでダウンロード（その場で生成）／「すべて持ち出す」は準備開始（非同期）→ 完了の知らせ → 7 日有効のリンク
- **例外・バリデーション**: CSV の文字コードは Excel で文字化けしない形にする。削除済み顧客は含めない。要配慮情報（禁忌・肌状態）も含まれるため、ダウンロードの事実を監査ログに残す。スタッフ・スクールは実行できない
- **受入基準**:
  - 顧客 CSV の行数が画面上の顧客数と一致し、Excel で開いて文字化けしない
  - 来店 CSV を「直近3か月」で出すと、その期間の来店記録だけが含まれる
  - 一式に預けた書類の原本が元のファイル名で含まれる
  - 失効後のリンクでは取得できない

## 3. スコープ

各機能を優先度で 4 区分に振り分ける。**この振り分けは暫定**で、友人ヒアリング（誰が払うか、録音か音声メモか、スクールが見る範囲、業態の内訳、スプレッドシートの内容）で入れ替える。

| 区分 | 意味 |
|------|------|
| **Scope 1（初版）** | まず必ず作る。MVPとして成立させる最小機能 |
| **Scope 2（改善）** | 初版の次に着手する改善・拡張機能 |
| **Scope 3（余裕があれば）** | 時間・リソースに余裕があれば実装する機能 |
| **Out of Scope** | 今回は明確に実装しないと決めたもの |

**外部ツール連携の優先順位の決め方**: 連携先は推測で決めず、FUNC-01 で申告してもらう「使っている入口・既存ツール」と、FUNC-23 で見える生徒サロン全体の割合から決める。技術的に可能な連携（LINE）と不可能な連携（公開 API の無い予約サイト）を分けて扱う。

**Scope 1 の線引きの考え方**: 「記録ゼロの店が、紙を捨てずに、最初の1件を作り、翌日も続けられる」状態を最小で成立させる。AI パイプラインは初版では2本（紙取り込み・音声メモ）に絞り、書類の抽出は Scope 2 に送る。前回の実測（画面 14 枚・テーブル 12 個で利用枠が尽きた）を上限として、初版の画面数をその範囲に収める。

### Out of Scope（今回は実装しない）

| 項目 | 実装しない理由 |
|------|----------------|
| 予約管理・予約サイトとの連携 | 既存の予約サイトと共存する前提（①未確定 2）。予約はそちらに任せ、本ツールは記録に専念する。**「今日の流れ」は予約表ではなく、次回予約日・今日の記録・手で足した人だけが並ぶと画面に明記する**（FUNC-29）。外部の予定は FUNC-31（Scope 3）で候補として取り込む。**ただし「次回予約日」は来店記録に任意で持つ**（次回予約率と再来店推奨のため）。キャンセル率などの分析が必要になれば予約サイトの CSV を FUNC-21 で任意に取り込む |
| 会計・POS・物販の売上管理 | 既存の会計アプリと共存し、レジ・決済・レシートは作らない。**ただし「来店ごとの金額（施術／物販／コース消化）」は来店記録に任意で持つ**（客単価・LTV・メニュー別売上のため）。メニューマスタ（FUNC-26）で入力負荷を下げる |
| LINE 公式アカウントとの API 連携 **を初版で行うこと** | 初版は接続設定の伴走コストを避け、フォームはリンクで開く形（FUNC-10）、送付はコピーで貼る形（FUNC-20）で成立させる。**Scope 2 で FUNC-27 として実装する**。外部 ID の受け皿は初版から持つ |
| 予約サイト（サロンボード等）との API 連携 | **公開 API が存在しないため不可**。連携をうたう周辺ツールも CSV や予約通知メールの読み取りで実現している。本ツールは顧客一覧の CSV 取り込み（FUNC-11）と、分析用の予約 CSV 取り込み（FUNC-21 内・任意）で対応する |
| 美容医療クリニック向け予約アプリ（カンナムオンニ等）との連携 | 対象が医療機関で、生徒サロンの業態と異なる可能性が高い。ヒアリングで生徒が実際に使っている集客・予約ツールを確認し、出てきたものだけ検討する |
| ブラウザ内での長時間（施術中ずっと）の連続録音 | iOS Safari 等は画面ロックやアプリ切替で録音が止まる。連続録音はストア配布のアプリ版（ネイティブの殻）で実現し、Web 版は端末標準の録音アプリから取り込む（FUNC-14）。数分の音声メモ（FUNC-13）はブラウザ内でも問題ない |
| 既存ツールとの継続的な同期 | 持ち込みは1回きり（FUNC-11）。双方向同期は整合性の問題が大きい |
| 美容室固有の機能（カラー配合レシピ等） | 対象業種外（①） |
| 複数店舗を1オーナーが束ねる機能 | 対象は個人〜小規模サロン。必要になったらテナント構造を見直す |
| お客様自身が自分のカルテを閲覧するマイページ | 送付（FUNC-20）で代替。認証を顧客に持たせるコストが大きい |
| 検索のフィルタ・詳細条件（担当・来店日範囲・業種など） | 顧客数が数十〜数百人の規模では検索窓の部分一致で足りる。ホーム（FUNC-29）が日常の導線になり検索の出番自体が減る。来店記録本文の全文検索も初版では持たない |
| 特商法のクーリングオフ判定・中途解約の精算額の自動計算 | 該当有無（未確定 7）と法務確認が先。FUNC-22 では日付と金額を保持するに留める |
| 文字起こし・抽出の精度を上げるための独自モデル学習 | 外部 API の構造化出力で賄う。精度不足は「確認して直す」運用で吸収 |
| 誕生日 DM・顧客ランク・ポイント | 競合の定番だが、本プロダクトの差別化（入力させない・使うためのカルテ）に寄与しない。再来店の声かけ（FUNC-19）で代替 |

| カテゴリ | 要件 |
|---------|------|
| 性能 | スマホ・4G 回線で主要画面（ホーム・顧客一覧・顧客詳細・来店記録）の初期表示 3 秒以内。写真は端末側で縮小してから送信し、1枚 1MB 以下を目安にする。AI 処理（文字起こし・抽出・生成）は非同期とし、処理中であることをホームの「確認待ち」で示す。音声メモ 1 分の処理は 30 秒以内に候補が出る（暫定）。検索は入力のたびに 1 秒以内に絞り込まれる |
| 配布形態 | **お客様向けのページ（問診フォーム・送付文面のリンク）は常に Web** で、お客様にアプリは入れさせない。**サロン側のスマホ向けはストア配布の専用アプリを標準**（App Store / Google Play。2026-10-08 確定）。中身は同じ Next.js の Web 画面で、Capacitor 等のネイティブの殻が録音のバックグラウンド継続・カメラ・プッシュ通知・ホーム画面のアイコンを担う。画面の修正はサーバー側で反映し、殻の更新時だけストアに再提出する。PC・タブレットのブラウザからも同じ URL で使える（スクールの横断ビューは Web）。試用は TestFlight 等で生徒サロンに配る。Apple 開発者登録（年額）・初回審査（数日〜1週間）・iOS ビルド環境（Mac + Xcode）が運用に乗る。審査対策として、録音・カメラ・通知などネイティブ機能を初回提出から含める |
| オフライン | 電波の弱い店舗（地下等）を想定し、写真の撮影と音声メモの録音は電波が無くても端末に保持し、つながったら送る。閲覧はオンライン前提 |
| 価格・原価 | サロンあたりの月額（基本料 + AI 従量）の中央値が 1 万円以内（仮）に収まる原価構造。AI 実費は文字起こしと LLM を分けて機能別に計測し（FUNC-25）、従量で請求できる粒度で記録する。会話録音は送る前に無音・BGM 区間を削って文字起こし量を減らす |
| セキュリティ（認証・認可方針） | 認証方式: メールアドレス＋パスワード（8文字以上・連続失敗でロック・メールで再設定）／セッション有効期限: 「この端末を記憶する」で 30 日のスライド更新。停止・退職は即時失効／権限モデル: オーナー・スタッフ・スクールの3ロール。既定はサロン内全員が全顧客を使え、担当限定はオプション。スクールは配下サロンをすべて閲覧でき、編集はできない。**サロン間のデータ分離はアプリの認可より下の層（DB の行レベルセキュリティ）で構造的に保証**し、全テーブルで有効にする。ブラウザから DB へ直接アクセスする経路は作らず、すべてサーバー側を経由する。写真・音声・PDF・サイン画像の URL は短期有効の署名付きとし推測不能にする。エラー文言やログに資格情報相当（セッションキー・トークン・LINE チャネルシークレット）を含めない |
| 個人情報・法令 | 体質・肌状態・既往歴・禁忌は要配慮個人情報として扱い、取得同意（FUNC-15）を前提にする。写真は本人同意を前提にし、記録用と販促用を分ける。会話録音は当事者録音として同意記録を持たず、店内掲示等の案内を運用で行う。音声ファイルは文字起こし後 30 日で削除（暫定）。削除要求（FUNC-16）に応じる手順を持つ。契約書面の保管義務は特商法の該当有無（未確定 7）確定後に保管期間を定める。スクールは配下サロンの記録をすべて閲覧できる（編集不可）。閲覧ログをサロン側に残す。サロンは全データを持ち出せる（FUNC-30） |
| AI 利用の品質 | AI の出力は常に「候補」として人が確認してから保存する。読めない・聞き取れない箇所は空欄にし、捏造しない。禁忌に関わる内容は AI が勝手に注意点に書かず、禁忌登録を促す。上限到達時もデータの保存は止めず、AI 処理だけ保留する（FUNC-25） |
| 可用性 | マネージドサービス（Vercel + Supabase）に依存し、独自のサーバー運用をしない。DB は日次バックアップと直近 7 日の時点復旧（暫定）。障害時の目標復旧時間は 1 営業日以内。営業時間中（10〜20 時）の計画メンテナンスは行わない |
| 実行環境・リージョン・時刻 | DB・ストレージは東京リージョン。アプリの実行リージョンも東京（`hnd1`）に明示的に固定する。この設定は消しても全チェックが緑のまま通るため、設定値を検査するテストを置く。日付の判定（来店日の「今日」、ホームの境界、月次の集計）はすべて日本時間で行い、サーバーが UTC で動くことを前提に純粋関数に閉じる |
| ユーザビリティ | **スマホを主としつつ、タブレット・PC でも同じ Web アプリがそのまま使える**（レスポンシブ。端末別の別アプリは作らない）。スマホ幅（375px）で片手操作できる。タブレットは店の共有端末とお客様に渡す同意画面を想定し、PC はオーナーの事務作業とスクールの横断ビューを想定する。主要操作のタップ領域は 44px 以上。文字入力を伴う操作は「確認して直す」形にし、最初から打たせない。顧客を探す操作は検索窓1つで、条件を選ばせない。共有端末を想定し、施術者の切り替えを来店記録ごとに1タップでできる。各画面に空状態・ローディング・エラーの3状態を持ち、エラーは原因と直し方を書く。ラベルは常時表示。デザイン値はトークン経由のみ（`.claude/rules/design-guidelines.md`） |
| 保守性 | クリーンアーキテクチャの依存ルール（Presentation → Service → Repository）を守り、DB client 直叩きと LLM 呼び出しの Presentation 層への漏れを禁止する。全層にテストを持ち、TDD で進める。スキーマはマイグレーションファイルを正とし、追加はファイルを増やす。`.claude/memory.md` に決定・学びを記録する |
| 監査 | 来店記録の編集履歴（誰が・いつ・何を）、削除の事実、スクールの閲覧ログ、エクスポートの実行、同意の取得・撤回を残す。操作者の識別子は残すが資格情報は残さない |
